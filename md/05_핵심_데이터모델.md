# 부동산 웹사이트 핵심 데이터 모델

## 1. 범위

초기 스키마는 인증, 중개사무소, 매물, 광고 검수, 이미지, 찜, 문의, 신고, 제재, 변경 이력, 감사 로그를 포함한다. 실제 개인정보와 실매물은 입력하지 않는다.

## 2. 도메인별 모델

| 영역 | 모델 | 책임 |
|---|---|---|
| 계정 | `User`, `Session`, `AuthToken` | 사용자 상태, 서버 세션, 이메일 확인·비밀번호 재설정 토큰 |
| 중개 | `Agency`, `AgentProfile` | 중개사무소와 소속 공인중개사 승인 상태 |
| 매물 | `Property`, `PropertyAddress` | 물리적 부동산 정보와 주소 공개 수준 |
| 광고 | `Listing`, `ListingImage` | 거래 조건, 게시 상태, 격리·검사되는 이미지 |
| 이용자 기능 | `Favorite`, `Inquiry`, `Report` | 찜, 문의, 허위 매물 신고 |
| 검수·운영 | `ListingReview`, `Sanction` | 관리자 검수와 계정 제재 |
| 추적 | `ListingHistory`, `ListingPriceHistory`, `AuditLog` | 상태·가격·관리자 작업 이력 |

핵심 관계:

```text
User 1--0..1 AgentProfile N--1 Agency
Agency 1--N Property 1--N Listing 1--N ListingImage
User N--N Listing (Favorite)
User 1--N Inquiry N--1 Listing
User 1--N Report N--1 Listing
Listing 1--N Review / History / PriceHistory
```

## 3. 매물과 광고 분리

`Property`는 주소와 면적 등 물리적 대상을 표현하고 `Listing`은 해당 대상의 거래 광고를 표현한다. 같은 부동산이 시간 차이를 두고 다시 광고되거나 거래 유형이 달라지는 상황을 이력 손실 없이 처리한다.

광고의 현재 가격은 조회 성능을 위해 `Listing`에 두고, 모든 가격 변경은 같은 트랜잭션에서 `ListingPriceHistory`에 추가한다.

## 4. 광고 상태 전이

```text
DRAFT -> REVIEW_PENDING
REVIEW_PENDING -> APPROVED | NEEDS_CHANGES | REJECTED
NEEDS_CHANGES -> DRAFT
APPROVED -> PUBLISHED
PUBLISHED -> PAUSED | EXPIRED | COMPLETED
PAUSED -> PUBLISHED | EXPIRED
DRAFT | NEEDS_CHANGES | REJECTED -> DELETED
```

- 상태 변경은 전용 도메인 서비스에서만 수행한다.
- 상태 변경과 `ListingHistory` 추가는 하나의 데이터베이스 트랜잭션이다.
- `version` 필드로 낙관적 잠금을 적용하여 동시에 수정한 내용을 조용히 덮어쓰지 않는다.
- 게시 중 가격 변경은 관리자 재검수 조건을 별도 정책으로 정한 뒤 구현한다.

## 5. 가격과 주소

- 모든 원화 가격은 PostgreSQL `BIGINT`에 원 단위 정수로 저장한다.
- API에서는 JavaScript `BigInt` 직렬화 문제와 정밀도 손실을 피하기 위해 가격을 문자열로 반환한다.
- 거래 유형별 필수 가격 조합과 음수 금지는 데이터베이스 CHECK 제약으로도 보장한다.
- 주소는 `시도/시군구/읍면동`과 원문 도로명·지번·상세 주소를 구분한다.
- 기본 공개 수준은 `APPROXIMATE`이며 검색 결과에 상세 주소를 노출하지 않는다.
- 위도·경도는 둘 다 있거나 둘 다 없어야 하며 유효 범위를 CHECK 제약으로 제한한다.

## 6. 삭제와 보존

- 사용자, 중개사무소, 부동산, 광고는 우선 소프트 삭제한다.
- 세션·일회용 인증 토큰과 찜은 상위 계정 삭제 시 정리할 수 있다.
- 문의, 신고, 검수, 제재, 가격·상태 이력은 운영 조사에 필요하므로 임의 연쇄 삭제하지 않는다.
- 개인정보 보존 기간과 익명화 기준은 실제 공개 전에 법률 검토 후 확정한다.

## 7. 이미지 안전성

업로드 직후 `UPLOADED`, 검사 중 `SCANNING`, 안전한 재인코딩 완료 후 `READY`, 실패 시 `REJECTED`로 이동한다. 공개 화면은 `READY` 이미지만 사용한다.

`object_key`, MIME 유형, 크기, 해상도, SHA-256을 저장한다. 원본 파일명은 신뢰하지 않으며 스토리지 키에 사용자 입력을 직접 사용하지 않는다.

## 8. 감사와 개인정보 최소화

- `AuditLog`는 행위, 리소스 종류와 ID, 요청 ID, 최소 메타데이터만 저장한다.
- 비밀번호, 쿠키, 토큰, 상세 문의 내용은 감사 메타데이터에 기록하지 않는다.
- IP와 User-Agent는 원문 대신 HMAC을 사용한다.
- 감사 로그의 수정·삭제 권한은 애플리케이션 일반 DB 역할에서 제거할 예정이다.

## 9. 데이터베이스 제약

Prisma가 직접 표현하지 못하는 다음 조건은 초기 SQL 마이그레이션에 수동 제약으로 추가했다.

- 로그인 실패 횟수와 면적·층·방·욕실·이미지 크기의 비음수 또는 양수 조건
- 세션과 일회용 토큰의 만료 순서
- 이메일 소문자 기준 유일 인덱스
- 위도·경도 쌍과 범위
- 매매·전세·월세별 가격 필드 조합
- 게시·만료 시각 순서
- 제재 시작·종료 시각 순서

## 10. 마이그레이션

초기 마이그레이션은 `packages/db/prisma/migrations/20260904022000_init/migration.sql`에 생성했다.

- 로컬: `npm.cmd run db:migrate`
- 스테이징·운영: `npm.cmd run db:deploy`
- 상태 확인: `npm.cmd run db:status`

Docker의 빈 PostgreSQL 18 데이터베이스에 초기 마이그레이션을 적용했다. `db:status`가 최신 상태임을 확인했고, 핵심 모델 테이블 17개와 Prisma 이력 테이블 1개, 수동 CHECK 제약조건 9개가 생성된 것을 직접 검증했다.
