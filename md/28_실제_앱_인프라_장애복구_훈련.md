# 실제 앱 인프라 장애·복구 격리 훈련

## 목적과 범위

장애 감지 응답만 흉내 내는 테스트가 아니라 PostgreSQL·Redis·MinIO·ClamAV 컨테이너를 각각 실제 중단·시작하여 API가 살아남고 정상 동작으로 돌아오는지 확인했다. DB는 매물·사용자 정보를 보관하고, Redis는 로그인 요청 제한·캐시를 담당한다. MinIO는 사진 파일을 보관하고 ClamAV는 사진 검사에 사용된다. 이들 중 하나가 멈췄을 때 전체 서버가 종료되거나 검사되지 않은 사진이 공개되는 것을 방지하는 것이 목적이다.

기존 `.env`·원본 DB·사진·백업을 훈련 입력으로 사용하지 않았다. 실행별 내부 Docker 네트워크, 무작위 임시 자격 증명, 신규 데이터 볼륨 3개, 컨테이너 6개를 사용했다. 포트 공개·외부 네트워크 연결은 없다. 기존 컨테이너 중단·삭제·재배포 명령은 실행하지 않았다. 작업 시작 시 Docker 엔진이 꺼져 있어 엔진을 시작했으며 기존 서비스는 자체 재시작 정책에 따라 시작되었다.

API는 로컬에 있는 기존 Linux 의존성 이미지에 현재 빌드한 `apps/api/dist`를 읽기 전용으로 연결해 실행했다. 보고서의 API 이미지 ID만으로 수정된 코드 전체를 식별할 수 있는 것은 아니다. `drill:app`은 실행 직전 API를 빌드한다. 테스트 환경은 `APP_ENV=staging`이므로 Redis 장애 시 운영용 요청 보호 차단 정책을 검사한다. 내부 HTTP 및 수동 쿠키 전달을 사용하므로 HTTPS·실제 브라우저 쿠키 정책 검증은 아니다.

ClamAV는 실제 `clamd` 프로세스를 사용하지만 정의 파일은 무해한 문자열을 대상으로 하는 훈련용 규칙 1개뿐이다. 원본 검사기·정의 파일을 공유하거나 최신 정의 파일을 다운로드하지 않았다. 따라서 **검사기 통신·중단·재시도 시험이지 실제 악성코드 탐지 성능이나 운영 정의 파일 검증이 아니다.** 대체 정의 파일 경로와 ndb 형식은 [ClamAV 공식 설정 안내](https://docs.clamav.net/manual/Signatures.html), [확장 시그니처 안내](https://docs.clamav.net/manual/Signatures/ExtendedSignatures.html)를 참고했다.

## 발견한 문제와 수정

1. DB 중단 후 사진 처리 스케줄러의 최상위 DB 조회 오류가 처리되지 않은 Promise 거부로 남았다. 초기 재현 실행 `39d8ec0b-e4df-4692-b3a5-8f0c96319768`에서 테스트 API 종료 코드 1, OOM 아님, 재시작 0을 확인했다. 백그라운드 진입점에서 오류를 잡고 다음 2초 주기에 다시 시도하도록 수정했다. 직접 호출하는 `processDueImages()`의 오류는 호출자에게 계속 전달하고, `finally`의 실행 잠금 해제도 유지한다. 예외 원문을 새 로그에 출력하지 않는다.
2. API 종료를 막은 뒤에도 DB 장애가 일반 500으로 반환되는 경로를 발견했다. 중지된 Docker 서비스의 이름 조회가 `EAI_AGAIN`으로 실패했고, 설치된 pg/Prisma 어댑터가 이를 Prisma 오류로 감싸지 않는 경우였다. 알려진 일시적 Prisma 연결 오류와 **설정된 DB 호스트의** 임시 이름 조회 오류만 503으로 바꾼다. 다른 서비스 오류·인증 실패·일반 트랜잭션 버그는 원래 처리를 유지한다.
3. DB·Redis 보호 서비스 장애에는 한국어 안내, 안정적인 오류 코드, `Cache-Control: no-store`, `Retry-After: 3`을 제공한다. 요청 재전송은 자동 수행하지 않는다. Redis의 local/test 허용 및 staging/production 차단 정책은 변경하지 않았다.

예외 필터의 위임 방식은 [NestJS 공식 문서](https://docs.nestjs.com/exception-filters), Prisma 오류 분류는 [공식 오류 문서](https://docs.prisma.io/docs/orm/reference/error-reference)와 설치된 드라이버 코드를 함께 확인했다.

사진 대기 상태에서는 공개 이미지 API가 404를 반환했다. 복구한 두 사진은 각각 완료 이력 1건만 기록되었고, 각 2개 객체(전체 사진·썸네일)의 저장소 내용과 HTTP 응답을 디코딩했다. 전체 시나리오 동안 API의 시작 시각은 동일하고 재시작 횟수는 0이다.

보고서의 `readinessPoll: true` 실패 항목은 최초 API 기동 직후 준비 대기 중 연결 실패이며, 이후 정상 응답 확인 후 장애 주입을 시작했다. 실제 시나리오 실패를 숨기거나 통과로 바꾼 것이 아니다.

## 반복 실행과 안전장치

```powershell
npm.cmd run test:drill:app
npm.cmd run drill:app
```

Docker 엔진과 스크립트에 고정된 로컬 이미지가 필요하다. 이미지가 없으면 자동 다운로드하지 않고 실패한다. 원본 프로젝트 Compose를 사용하거나 환경변수로 목적지를 바꾸지 않는다. 추가 CLI 인자도 허용하지 않는다.

정리는 실행별 소유 레이블과 정확한 컨테이너·네트워크 ID, 생성한 볼륨 이름을 확인한 뒤 수행한다. 다른 실행이나 원본 자원은 삭제하지 않는다. 최종 실행은 컨테이너 6개·볼륨 3개·네트워크 1개를 정리했다. 훈련용 계정·사진도 함께 폐기되며 원본 복구 대상이 아니다. 검증 보고서는 로컬에 남는다. 강제 프로세스 종료나 Docker 엔진 장애로 정리가 실패하면 보고서·레이블을 확인하여 그 실행 자원만 별도로 정리해야 한다.

## 적용 상태·남은 범위

- 이 훈련 당시에는 기존 API에 재배포하지 않았다. 후속 [29번 작업](./29_API_로컬서버_안전배포_및_검증.md)에서 2026-09-06 13:01:03 KST에 기존 로컬 API 교체와 정상 로그인·사진 업로드 검증을 완료했다.
- 단일 의존성의 짧은 중단을 검증했다. 장시간 장애의 재시도 5회 소진, 10분 이상 SCANNING 잔류 복구, 처리 도중 DB 커밋 실패, 네트워크 무응답·지연, 디스크 부족·손상, 동시 다중 장애·부하 시험은 별도다.
- 사진은 실제 업로드 HTTP 경로 대신 격리 DB/S3의 업로드 완료 상태부터 주입했다. 사진 선택·전송 중 실패 및 웹 화면의 오류 렌더링·실기기 터치는 이번에 검증하지 않았다.
- 외부 주소 전송·외부 경보 수신 채널, 백업 암호화·ACL은 계속 보류 상태다.
- 롤백은 이번 스케줄러 진입점·예외 필터 등록·Redis 안내·훈련 명령 추가를 되돌리고 이전 API 이미지로 교체하는 방식이다. DB 스키마 변경·원본 데이터 복원은 필요 없다. 스케줄러 보완을 되돌리면 재현한 DB 장애 시 종료 위험도 다시 생긴다.
