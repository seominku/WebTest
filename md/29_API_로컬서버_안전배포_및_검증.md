`compose up --no-deps --no-build api`로 기존 API 컨테이너만 새 이미지로 교체했다. 다른 서비스 및 데이터 볼륨을 교체·삭제하지 않았다. DB 마이그레이션·시드 실행·백업 삭제는 없었다. 정상 검증에 사용한 임시 계정·초안 매물·사진은 기존 스모크 도구의 해당 ID 정리 경로로 폐기했다. Redis의 임시 요청 제한·캐시 항목은 각 TTL에 따라 만료된다. 전체 Redis 삭제는 하지 않았다.

## 배포 전 해결한 두 가지 문제

1. **원래 이미지 없음:** 실행 중인 API는 정상이지만 그 이미지 참조를 로컬 이미지 목록에서 찾을 수 없어 단순 태그 복사에 실패했다. 교체 전에 중단했다. 기존 API에 데이터 마운트가 없고 `docker diff`가 비어 있으며 알려진 `.env` 경로가 없는 것을 확인한 뒤, 컨테이너 파일 시스템을 바이너리 스트림으로 export/import했다. 실행 환경변수는 복사하지 않고 `NODE_ENV`·`PATH`와 확인된 실행 사용자·경로·명령만 설정했다. 복구 이미지의 ENV 키가 이 둘뿐임을 확인했고, 재사용 전 기존 컨테이너와 API/DB 패키지 빌드 디렉터리의 SHA-256이 일치하는지도 확인했다. 전체 이미지의 비밀정보 정적 스캔이나 실제 운영 복구 전 과정을 수행했다는 의미는 아니다.
2. **마운트 반환 순서:** 빌드 뒤 비 API 서비스 비교에서 차이가 감지되어 교체 전에 멈췄다. 컨테이너 ID·이미지·시작 시각은 동일했다. Docker의 마운트 나열 순서에 영향을 받지 않도록 목적지 경로 순으로 정렬해 비교하도록 수정하고 회귀 테스트를 추가했다. 실제 볼륨 이름·목적지 변경은 계속 감지한다.

파일 시스템 내보내기와 이미지 실행 설정 재구성은 [Docker export 공식 문서](https://docs.docker.com/reference/cli/docker/container/export/), [Docker import 공식 문서](https://docs.docker.com/reference/cli/docker/image/import/)를 참고했다. 컨테이너 실행 환경변수가 이미지에 들어갈 수 있는 commit 대신 이 경로를 사용했다. [Docker 환경변수 주의사항](https://docs.docker.com/reference/cli/docker/)

복구 이미지는 Docker 표시 기준 약 896MB이며 로컬에 보관한다. 태그가 여러 개여도 같은 이미지 ID를 가리키는 태그마다 전체 파일이 복제되는 것은 아니다. 보관 이미지를 자동 삭제하지 않았다.

## 적용 후 검증

- 새 이미지의 파일에서 스케줄러 오류 수습·DB 오류 필터·요청 보호 오류 코드와 필터 등록을 확인한 뒤 시작했다.
- 인증 스모크 7항목: 가입·이메일 토큰 확인·로그인·인증 사용자 조회·CSRF 교체·로그아웃·폐기 세션 거부.
- 매물/사진 스모크 13항목: 중개사 로그인·초안 생성·면적 정수/소수·소유 목록·버전 수정·충돌 거부·비공개 초안·사진 검사·WebP 변환·썸네일·소유자 전용 접근·사진 삭제·변경 이력.
- 이 사진 검증은 기존 서버에 연결된 실제 ClamAV와 MinIO를 사용한 정상 업로드 시험이다. 이번 배포 작업 중에는 원본 인프라를 고의로 중단하지 않았다.
- 기존 공개 매물 5개와 첫 페이지 ID 집합 동일. 전체 DB 내용 해시의 전후 비교는 아니다.
- 운영 상태 10항목 정상. 배포 후 추가 사전 검사에서도 새 이미지와 설정 일치 확인.
- 사진 사전 점검: DB 이미지 5행(READY 4·REJECTED 1), 진행 중 0, READY 사진 객체 8개·199,874바이트의 HEAD 메타데이터 정상. 이 점검은 콘텐츠 해시나 추가 복원 증명은 아니다.
- 배포 안전 비교 테스트 6개·JavaScript 문법·서식 검사 통과. 일회성 검증 컨테이너 잔여 없음.

실제 브라우저·휴대폰에서 사용자 입력을 조작한 테스트는 이번 범위가 아니다. 스모크 테스트의 이메일 인증은 기존 local 응답 토큰을 사용하며 외부 이메일 발송을 검증하지 않는다.

## 반복 실행

```powershell
npm.cmd run deploy:api:check
npm.cmd run test:deploy:api
npm.cmd run deploy:api:local
```

`check`는 서버를 변경하지 않고 로컬 보고서만 남긴다. `local`은 API 이미지 빌드·교체와 임시 데이터 생성/정리를 수행하므로 점검 시간에 실행한다. 빌드 과정에서 기본 이미지 메타데이터·npm 의존성 등을 조회할 수 있지만 소스·고객·매물 정보를 외부 서비스에 업로드하는 절차는 없다. `.env`·백업·`.artifacts`는 Docker 빌드 제외 규칙을 유지한다.

스크립트는 실행할 때 기존 서비스가 모두 정상이어야 하고, 기존 API 환경과 Compose 설정이 다르면 중단한다. 최종 보완본은 빌드 직전/이후 API 설정 변경 및 배포한 이미지/환경 불일치도 검사한다. 보완 후 `check`와 비교 단위 테스트는 실행했으며 동일 API의 불필요한 재배포는 하지 않았다. 임시 데이터 스모크가 실패하면 API 이미지를 되돌리는 경로가 있다. 이번 성공 배포에서는 실제 자동 롤백 경로를 발동하지 않았으므로 롤백 종단 훈련 완료로 보지 않는다.

## 필요할 때 되돌리기

먼저 현재 실행 ID·API 이미지·설정 및 복구 이미지가 여전히 존재하는지 확인한다. 아래는 작업 폴더에서 이번 배포를 되돌릴 때 사용할 명령이며 이번에 실행하지 않았다.

```powershell
docker compose --project-name real-estate-platform --env-file .env -f docker-compose.yml -f .artifacts/api-deploy-717ad3d9-e249-45d6-a58a-799d19e907eb/rollback.compose.json up -d --no-deps --no-build api
docker image tag sha256:b65f6c0a95d46b983d2afcaeff417f237c0ae970143f7b9c81f7c3d4b0d69d5f real-estate-platform-api
npm.cmd run ops:check
```

API만 이전 실행 파일로 복귀하며 DB·사진 백업을 복원하는 명령이 아니다. 이전 코드로 돌아가면 28번에서 확인한 장애 시 종료 위험도 다시 생긴다. `.env`가 그사이 변경되었다면 이전 설정과 먼저 비교해야 한다.
