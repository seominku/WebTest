# 모바일 레이아웃 점검

## 방법과 범위

computer-use 스킬의 브라우저 제어를 사용해 로컬 Chrome의 화면 폭을 320, 390, 768, 1440px로 변경하며 검사했다. 사진, 지도 패널, 등록 입력창, 면적 단위, 메뉴를 실제로 조작했다. 이 검사는 브라우저 반응형 레이아웃 검증이며 실제 iPhone/Safari·Android의 터치·가상 키보드 검증을 대신하지 않는다.

## 발견 및 수정

- **작은 화면에서 사진 이동 버튼 잘림:** 320px에서 썸네일 줄의 최소 너비가 갤러리 전체를 약 328px로 늘려 약 273px 사진 영역에서 버튼과 사진 번호가 잘렸다. 갤러리의 최소 너비를 0으로 허용하고 부모를 너비 제한이 있는 단일 열로 지정했다. 썸네일 줄만 가로 스크롤되고 큰 사진과 조작 버튼은 고정된 화면 폭을 사용한다.
- **화살표 식별 어려움:** 갤러리 부모의 흰 글자색이 흰 버튼에 상속됐다. 화살표를 짙은 색으로 지정하고 버튼을 44px 정사각형으로 키웠다.
- **상세 정보 영역 너비:** 상세 본문에 최소 너비 0과 제한된 열 너비를 적용하고 작은 화면의 정보 카드 여백을 줄였다. 두 칸 정보와 면적 단위 버튼을 화면 안에 유지한다.
- **지도 패널 이중 스크롤:** 모바일에도 420px 높이 제한이 적용돼 페이지와 정보 패널을 따로 스크롤해야 했다. 1024px 미만에서는 지도 아래로 내용 전체를 펼치고, PC에서만 420px 옆 패널과 내부 스크롤을 유지한다.
- **선택 전 지도의 빈 공간:** PC에서 선택한 매물이 없어도 오른쪽 320px 칸이 예약되던 구조를 변경했다. 패널이 없으면 지도 전체 폭을 사용한다. 패널 닫기 버튼도 44px로 확대했다.

변경 파일: `listing-photo-gallery.tsx`, `listing-map.tsx`, `app/listings/[id]/page.tsx`.

## 영향과 복구

- 사진 내용, 면적 환산식, API·권한·외부 연동 설정은 변경하지 않았다. 새 매물·문의·방문 데이터도 저장하지 않았다.
- 이번 3개 파일의 레이아웃 클래스 변경만 되돌린 뒤 Web 이미지를 재빌드하면 복구할 수 있으나 작은 화면 사진 잘림이 재발할 수 있다.
- 다음 보완 후보: 실제 모바일 기기에서 터치 스크롤과 키보드 표시 중 입력창 가림 점검.

## 2026-09-05 18:19:46 KST - 짧은 화면 메뉴 및 입력 사용성

- 범위: Chrome 뷰포트 390×360. 실제 휴대폰 키보드나 터치 이벤트를 재현한 검사가 아니라 높이가 짧은 화면의 대체 레이아웃 검사다.
- 문제 재현: 로그인 상태의 메뉴 하단이 화면 높이 360px보다 낮은 약 408px에 위치해 마지막 항목이 잘렸다. 문의 내역을 선택해도 메뉴의 `open` 상태가 유지됐다.
- `mobile-nav.tsx` 변경: 현재 뷰포트 높이에서 상단 여유를 뺀 최대 높이와 내부 스크롤 적용. 메뉴 링크 선택 시 닫힘, Esc로 닫기 및 메뉴 버튼 포커스 복원 추가. 내비게이션 이름도 지정했다.
- 재검증: 메뉴 하단 약 338px로 화면 내부 유지, 콘텐츠 높이 348px를 표시 높이 278px 안에서 스크롤 가능. 마지막 내 계정 링크 이동 성공, 링크 선택 후 `open=false`, Esc 후 `open=false` 및 `SUMMARY` 포커스 확인.
- 입력 설정: 면적 `inputMode=decimal`, 우편번호 `inputMode=numeric` 기존 설정 유지. 면적 84.92 입력 시 입력창 상단 약 156px·하단 약 205px로 높이 360px 안에 표시. 문서 폭과 사용 가능 폭 모두 375px.
- Web 린트·타입 검사 및 Docker 프로덕션 빌드·재배포 통과. 점검 입력은 저장하지 않았으며 뷰포트 복원 완료.
- 영향/복구: 인증·매물 데이터·API·외부 접속 설정 변경 없음. `mobile-nav.tsx`의 이번 변경만 복원하고 Web 재빌드 가능. 실제 모바일 OS별 키보드 동작은 실기기 연결 후 별도 확인이 필요하다.
