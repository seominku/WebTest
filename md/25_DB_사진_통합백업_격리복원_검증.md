## 백업 보관 위치

실행 ID: `759f1a91-15ec-4b0c-8bfb-68131bdd052e`

프로젝트 아래 `backups/recovery-759f1a91-15ec-4b0c-8bfb-68131bdd052e/`에 다음 파일을 보관했다.

- `database.dump`: PostgreSQL custom 형식 덤프, 96,369바이트
- `asset-0001.webp`~`asset-0008.webp`: READY 본문·썸네일 복사본, 합계 199,874바이트
- `sample-0001.webp`~`sample-0003.webp`: 앱에 포함된 정적 샘플 사진 복사본
- `manifest.json`: DB 테이블 검증값, 사진 참조·복사 파일·새 해시 연결 정보
- `verification.json`: 복원·결함 감지·정리 결과

**이 백업은 계정 정보·비밀번호 해시·DB 인증 기록·문의·사진 등을 포함할 수 있는 비암호화 민감 파일이다.** `backups/`의 Git·Docker 빌드 제외는 암호화를 의미하지 않는다. 외부 업로드하지 않았으며 Windows 계정·디스크 접근 통제와 보관 정책은 별도 관리해야 한다. POSIX 파일 모드 요청만으로 Windows ACL 보호를 보장하지 않는다.

초기 실행 매니페스트의 제외 설명 `secrets and Redis sessions`는 환경변수의 비밀값·Redis 저장 상태를 뜻한다. DB에 들어 있는 인증 관련 행은 덤프에 포함된다. 후속 실행 코드의 설명을 더 명확하게 수정했으며 검증 완료 백업은 덮어쓰지 않았다.

## 실행 명령과 전제

```powershell
npm.cmd run test:recovery
npm.cmd run recovery:verify
```

`recovery:verify`는 매번 새 백업을 만들고 그 백업을 복원 검증한다. 후속 작업으로 기존 백업만 지정하는 `recovery:restore -- backups/recovery-실행ID`를 추가했으며, 원본 미접근 검증 결과는 [26번 문서](./26_원본없이_기존백업_복원검증.md)에 기록했다.

필요 조건은 실행 중인 로컬 PostgreSQL·MinIO, `.env` 연결 설정, Docker Desktop, 설치된 npm 의존성, 코드에 고정한 로컬 이미지다. 기존 앱 API 이미지는 Node·pg·S3·sharp 도구 제공용으로만 사용하며 앱 서버를 실행하지 않는다. helper 이미지 ID는 이 PC에서 검증한 `sha256:ac92aedf39f151cec7687cfa64b67f6a7330fe8097dfaf74b706541a7189f94a`로 고정되어 있어 다른 PC에서는 동일 검사 환경을 별도로 준비해야 한다. 이미지 자동 다운로드·기존 앱 재빌드는 하지 않는다.

로컬 훈련의 자원 제한: public 테이블 최대 100개, 행 합계 최대 100,000개, 사진 레코드 최대 1,000개, 개별 READY 객체 최대 16MiB, READY 객체 합계 최대 256MiB. 한계를 넘는 데이터는 별도 대용량 절차를 설계해야 한다. 제한값은 운영용 확장성을 보장하지 않는다.

## 일관성과 검증 방법

1. 원본 Compose 프로젝트·서비스·DB 이름·사용자·호스트 포트를 대조한다. 원본 연결은 읽기 전용이며 쓰기 명령을 실행하지 않는다.
2. `REPEATABLE READ READ ONLY` 트랜잭션에서 `pg_export_snapshot()`으로 스냅샷을 내보내고, 사진 목록·테이블 내용과 `pg_dump --snapshot`이 같은 DB 스냅샷을 사용한다. 내보낸 트랜잭션은 덤프가 끝날 때까지 유지한다. [PostgreSQL 스냅샷 동기화 문서](https://www.postgresql.org/docs/current/functions-admin.html)
3. READY 본문·썸네일을 HEAD로 확인한 뒤 ETag 조건부 GET으로 복사한다. 복사 바이트에서 새 SHA-256을 계산하며 DB의 업로드 당시 해시를 변환 사진 해시로 오해하지 않는다. 누락·크기 불일치·복사 중 변경은 실패 처리한다.
4. 복사 후 저장소 ETag·크기를 다시 확인하고, 트랜잭션 종료 후 사진 참조 목록도 다시 조회해 변경 여부를 검사한다. 처리 중 사진이 있으면 시작하지 않는다.
5. 별도의 고유 실행 ID로 내부 Docker 네트워크와 PostgreSQL·MinIO를 생성한다. 호스트 포트를 공개하지 않는다. 임시 데이터는 tmpfs에만 저장하고 임시 비밀번호를 생성한다. 원본 인증정보는 복원 컨테이너에 전달하지 않는다.
6. 임시 DB에만 덤프를 복원한다. 검사 도구는 읽기 전용 백업 마운트를 사용해 DB 테이블별 내용 해시·사진 관계·순서·대표 순서 정보를 대조하고 임시 MinIO에 사진을 업로드한다. 모든 READY 참조가 매니페스트 객체 목록에 포함되는지 확인한다.
7. 임시 저장소에서 사진을 다시 읽어 복사본 해시·크기·형식·디코딩을 확인한다. 샘플 사진은 읽기 전용 마운트의 복사본을 검증하며 실제 웹 배포 경로로 설치하지는 않는다.
8. 임시 객체 한 개에만 삭제·변조 시험을 수행하고, 감지가 성공하면 원래 백업 바이트로 복구한 뒤 모든 객체를 재검사한다.
9. 생성 자원의 `recovery.run` 레이블과 전체 ID를 대조한 후 이번 자원만 제거한다. 소유 확인이나 정리가 실패하면 성공 처리하지 않는다. 백업 파일은 자동 삭제하지 않는다.

DB와 사진 저장소 사이에 공통 원자적 스냅샷 기능이 추가된 것은 아니다. 이 도구는 동일 DB 스냅샷, 앱의 READY 키 참조 방식, 조건부 복사 및 변경 재검사로 이번 묶음의 일관성을 확인한다. 외부에서 같은 객체를 변경·원복하는 모든 경합을 입증하거나 제거하지 못한다. 엄격한 운영 시점 복구에는 객체 버전 관리·쓰기 동결 등 추가 설계가 필요하다.

## 포함하지 않는 범위

- REJECTED 사진 레코드는 DB에 보존되지만 격리 파일·거절 파일·버킷 고아 객체는 복사하지 않는다. 업로드 원본이 처리 후 삭제된 경우 그 원본을 복구한 것도 아니다.
- `.env` 비밀값, Redis 상태, DB 클러스터 역할·원래 소유권·권한은 복원하지 않는다. 덤프 복원은 `--no-owner --no-privileges`로 수행한다.
- 테이블별 내용·관계 일치를 확인했으나 모든 시퀀스 상태·전역 객체를 개별 대조한 것은 아니다.
- 복원된 앱 서버·로그인·지도·메일·전체 UI를 실행한 시험은 아니다. 원본 앱과 스케줄러는 중단하지 않았다.
- 로컬 한 시점의 복구 훈련이며 원격 재해 복구·암호화·자동 보관 주기·성능 기준·복구 시간 목표를 완료한 것은 아니다.

## 정리와 변경 기록

이번 컨테이너 3개·네트워크 1개를 정리했고 실행 ID 레이블로 잔여 컨테이너·네트워크가 없는 것을 재조회했다. 프로젝트의 영구 볼륨도 없었다. 임시 복원 DB·사진은 삭제됐지만 로컬 백업은 남아 있어 재복원할 수 있다. 원본 DB·버킷·기존 서버는 변경하지 않았다.

추가 파일은 `scripts/recovery-bundle-check.mjs`, `recovery-target.mjs`, `recovery-common.mjs`, 공통 검사 테스트다. package.json 명령 2개를 연결했다. 새 의존성 설치나 앱 재빌드는 하지 않았다. 단위 테스트 31개, JavaScript 문법·포맷 검사, 실제 복원, 원본 사전 점검 및 외부 전송 비활성 확인이 통과했다.

코드만 되돌리려면 이번 파일 4개와 명령 추가를 제거하면 된다. 백업 파일은 민감 자료이므로 별도 보관·삭제 결정을 따르며 코드 복구 과정에서 자동 삭제하지 않는다. 원본 연결 없는 검증 경로는 26번 작업에서 완료했다. 남은 우선순위는 백업 접근 통제·암호화·보관 주기와 운영 복구 절차 보완이다.
