# 실제 모니터링 격리 훈련 구성

## 목적과 구분

이전 21번 훈련은 모의 HTTP 서버의 응답을 점검했다. 이 구성은 실제 Prometheus와 Alertmanager가 가상 지표 서버의 중단을 감지하고 경보를 전달·해제하는지 확인하기 위한 실행 환경이다. 19:16에는 정적 구성 검증을 마쳤고, 23:34에는 실제 컨테이너에서 경보 발생·수신·해제를 확인한 후 훈련 자원을 정리했다.

`infrastructure/drill/compose.yml`은 기존 `docker-compose.yml`과 병합하지 않는 독립 구성이다.

- `exporter`: 실제 매물이나 개인정보 대신 숫자 1만 반환하는 가상 지표 서버
- `prometheus`: 5초마다 지표를 수집하고 연결 중단이 10초 지속되면 `DrillExporterDown` 경보 발생
- `alertmanager`: 경보를 받아 로컬 조회 API에서 확인. 이메일·Slack·웹훅 수신처 없음

## 격리 기준

프로젝트 이름은 `real-estate-drill`, 네트워크 이름은 `real-estate-drill_drill`이다. 기존 앱 프로젝트 `real-estate-platform`의 컨테이너·볼륨·네트워크는 참조하지 않는다.

- UI 포트는 루프백 전용 19090·19093, 가상 지표 서버는 호스트 포트 미공개
- 네트워크는 `internal: true`. Docker의 외부 격리 네트워크 옵션을 사용한다. 실제 런타임 연결 동작은 실행 단계에서 확인해야 한다. [Docker 공식 네트워크 문서](https://docs.docker.com/reference/compose-file/networks/)
- 바인드 마운트는 이 폴더의 지표 코드·설정 파일 4개만 읽기 전용으로 허용
- 영구 볼륨·앱 데이터·`.env` 마운트·Docker 소켓·계정 인증정보 주입 없음
- 컨테이너 루트 파일시스템 읽기 전용, Linux capability 제거, 권한 상승 방지
- 지표와 경보 상태는 크기가 제한된 tmpfs에만 저장. 컨테이너 중지 시 상태가 사라지므로 증거 확인은 정리 전에 수행
- 기존 앱의 5분·15분·30분 경보 기준은 변경하지 않음. 짧은 시간 기준은 훈련 전용

Prometheus·Alertmanager 이미지는 로컬에서 조회한 digest로 고정했다. 이번 실행에서는 공식 `node:24-bookworm-slim` 이미지를 내려받고 Node v24.20.0을 확인했다. Compose의 Node 이미지도 내려받은 `sha256:ba849c60be29959425b8734d57b8b4b7d56f98edd9504c9af091d5281095a71e` digest로 고정했다. Docker 이미지 다운로드는 레지스트리 네트워크 통신이며 컨테이너의 내부 네트워크 제한과 별개다. 계정·매물·주소 데이터를 다운로드 요청에 넣지 않았다.

## 현재 검증 명령

```powershell
npm.cmd run drill:config
npm.cmd run test:drill:config
```

Docker Compose CLI가 필요하지만 컨테이너를 생성하거나 시작하지 않는다. `config --format json` 결과를 메모리에서 검사하고 원문 환경 설정은 출력하지 않는다.

검사기는 프로젝트·서비스 목록·네트워크·포트·마운트·권한·환경 주입 등의 격리 조건을 확인한다. 원본 `compose.yml`의 선언과 이미지 내용, Prometheus 설정 의미 전체를 감사하는 도구는 아니다. 실행 명령을 자동으로 차단하는 보안 경계도 아니므로 파일 변경 후 반드시 다시 검사한다.

정상 구성 1개와 잘못된 구성 13개를 대상으로 총 14개 테스트가 통과했다. 기존 프로젝트 이름, 공용 바인딩, 기존 포트, 공유 네트워크, 영구 볼륨, 환경 주입, 권한 상승, 마운트 변경 등을 실패로 처리했다. 지표 서버 JavaScript 문법 검사도 통과했다.

## 반복 실행 절차

아래는 이번에 실행한 훈련을 반복하는 절차다. 현재 훈련 컨테이너는 정리된 상태다.

1. `drill:config` 통과 후 19090·19093이 비어 있는지 확인한다. 충돌하면 기존 프로세스를 종료하지 말고 실행을 보류한다.
2. Docker의 기존 `real-estate-drill` 자원이 있다면 소유·용도를 확인한다. 출처가 불명확하면 재사용하거나 정리하지 않는다.
3. 고정된 독립 Compose 파일과 프로젝트 이름을 명시해 시작한다.

```powershell
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill up -d
```

4. Prometheus에서 `drill-exporter` 수집 `up`과 경보 `inactive`를 확인한다. Alertmanager 조회 상태도 확인한다. 이번 Windows Docker 환경에서는 호스트 19090·19093 접속이 실패했으나 컨테이너 내부 조회는 정상이다. 호스트 접속 실패의 원인을 추가로 확정하지 않았으며, 내부 네트워크를 해제하지 않고 아래 조회를 사용했다. 설정 오류나 이미지 권한 오류가 있으면 장애 훈련 전에 해결한다.

```powershell
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill exec -T prometheus wget -T 5 -qO- http://localhost:9090/api/v1/targets
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill exec -T prometheus wget -T 5 -qO- http://localhost:9090/api/v1/rules
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill exec -T alertmanager wget -T 5 -qO- http://localhost:9093/api/v2/alerts
```
5. 컨테이너의 `com.docker.compose.project=real-estate-drill` 및 서비스 이름이 `exporter`임을 확인한 뒤 그 서비스만 중단한다.

```powershell
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill stop exporter
```

6. `up=0`, Prometheus 경보 `pending→firing`, Alertmanager에 `DrillExporterDown` 수신을 확인한다. 일정 시간 뒤 관찰되지 않으면 성공 처리하지 않고 수집·평가·전달 경로를 분리 진단한다.
7. 같은 서비스만 시작하고 `up=1`, 규칙 `inactive`, Alertmanager에서 더 이상 활성 경보가 아닌 상태를 확인한다.

```powershell
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill start exporter
```

8. 관찰 시각과 결과를 기록한다. 성공·실패에 관계없이 이번 실행이 만든 컨테이너인지 다시 확인한 후 훈련 프로젝트만 정리한다. 기존 앱에는 `down`을 실행하지 않는다.

```powershell
docker compose -f infrastructure/drill/compose.yml -p real-estate-drill down
```

9. 기존 앱 `npm.cmd run ops:check`를 실행해 현재 서비스가 정상인지 확인한다.

Alertmanager는 수신처 설정에 따라 전달한다. 이번 구성은 외부 수신처 없이 로컬 조회만 사용하므로 이메일·메신저 수신 확인을 의미하지 않는다. [Alertmanager 공식 설정 문서](https://prometheus.io/docs/alerting/latest/configuration/)

## 실제 실행 결과

기존 `real-estate-drill` 컨테이너·네트워크가 없고 19090·19093 리스너가 조회되지 않는 것을 확인했다. 새 컨테이너 3개와 네트워크 1개를 생성했다. Docker에서 프로젝트·서비스 레이블과 전체 컨테이너 ID를 확인한 뒤 이번 exporter ID만 중단·재시작했다. 네트워크 `Internal=true`와 연결된 서비스가 훈련 3개뿐인 것도 확인했다.

| 시각 KST | 관찰 근거 |
| --- | --- |
| 23:28:37 | 컨테이너 로그에서 Prometheus 설정 로드·준비 완료 확인. Alertmanager 로그 버전 v0.34.0 |
| 23:30:47~48 | 지표 수집 health=up, 규칙 inactive, Alertmanager 목록 빈 배열 |
| 23:31:28 | Prometheus 과거 시각 질의에서 `ALERTS{alertname="DrillExporterDown",alertstate="pending"}=1` 확인. 실시간 폴링에서는 pending 구간을 지나쳐 이력으로 검증 |
| 23:31:33 | Alertmanager startsAt=23:31:33.568, 이후 조회에서 같은 경보 active·수신처 drill-local-only 확인 |
| 23:31:38 | Prometheus 규칙 firing 및 평가 health=ok 확인 |
| 23:32:17 | exporter 재시작 후 수집 health=up, lastError 빈 값 |
| 23:32:38 | Prometheus 규칙 inactive 확인. 이어서 Alertmanager 목록 빈 배열 확인 |
| 23:34:01 | 훈련 정리 후 기존 앱 상태 점검 10항목 통과 |

Prometheus `promtool check config`와 Alertmanager `amtool check-config`도 실제 컨테이너에서 통과했다. 판정: 가상 지표 서버 장애에 대한 **실제 수집·평가·경보 수신·복구 해제 흐름 통과**. 이메일·Slack·웹훅 발송은 하지 않았다.

정리 전 이번 실행에서 기록한 전체 컨테이너 ID 3개와 네트워크 ID가 현재 자원과 일치하는지 확인했다. 훈련 전용 Compose `down`으로 컨테이너 3개와 네트워크 1개만 제거했고, 같은 프로젝트 레이블의 잔여 자원이 없는 것을 확인했다. tmpfs의 지표·경보 기록은 정리와 함께 소멸했으며 위 관찰 결과를 문서로 보존했다. 이미지 캐시는 재실행용으로 남겨 두었다.

## 한계와 복구

Compose 구문·격리 규칙과 실제 컨테이너의 경보 흐름은 검증했다. 호스트 UI 접속 문제의 근본 원인 및 실제 외부 목적지에 대한 통신 차단 시험은 하지 않았다. DB 복구·Redis 세션 복원·사진 검사 재시도·기존 앱의 사진 정리 경보 조건 자체는 이 구성에 포함되지 않는다.

이번 실행의 소스 변경은 Compose의 Node 이미지 digest 고정과 관련 문서 갱신이다. 이미지 고정만 복원할 수 있지만 검증 이미지 재현성을 위해 유지한다. 훈련 구성 전체 제거 방법은 신규 구성 파일 5개·검사 스크립트·테스트·명령 2개를 제거하는 것이다. 현재 훈련 Docker 자원은 정리되어 추가 컨테이너·볼륨 정리는 필요 없다. 훈련은 동일 설정으로 다시 실행할 수 있지만 삭제된 메모리상의 시계열 이력 자체는 복구되지 않는다.
