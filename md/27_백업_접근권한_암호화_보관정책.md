# 백업 접근 권한·암호화·보관 정책

## 현재 확인 결과

2026-09-06 02:29:49 KST, 로컬 `backups` 폴더에 파일 15개·총 908,387바이트가 있었다. 통합 백업의 14개 파일 외에 이전 DB 덤프 1개도 포함한다.

백업 루트·하위 폴더·파일의 17개 항목에서 상속된 접근 규칙과 추가 읽기 또는 쓰기 허용 규칙을 확인했다. 백업 소유자·SYSTEM·Administrators 외에 개발 작업용 계정/그룹 등의 권한이 상속되어 있다. 이것은 사용자 전용 접근 상태가 아니지만, 외부 공개나 유출을 관찰했다는 뜻도 아니다.

`backups/`가 Git·Docker 빌드에서 제외되어 있어도 파일 시스템 접근 제한이나 암호화가 자동 적용되는 것은 아니다. 현재 저장된 DB 덤프·사진·JSON은 응용 파일 수준 암호화로 보호하지 않았다. BitLocker·EFS 등 다른 디스크 보호 적용 여부는 이 점검에서 판정하지 않았다.

이번에는 ACL을 변경하지 않았다. 개발 환경에서 관리하는 접근 권한을 제거하면 이후 백업 점검·복원 작업이 막힐 수 있으므로, 허용할 주체와 도구 접근 방식부터 확인해야 한다.

## 추가한 읽기 전용 명령

```powershell
npm.cmd run backup:security
npm.cmd run test:backup:security
```

`backup:security`는 Windows에서 파일 수·크기·수정 시각·ACL 메타데이터를 조회한다. 내용·인증정보·사용자 이름·SID를 출력하지 않고 집계값만 반환한다. `.env`, 원본 DB·S3 연결, 파일 수정·암호화·삭제·ACL 변경은 수행하지 않는다.

심볼릭 링크·junction 등 reparse point는 따라가지 않고 별도 집계한다. 경로는 `backups` 내부로 제한하며 항목 수 상한은 10,000개다. 보고서의 `readableFormatFiles`는 확장자에 따른 검토 대상 분류이며 모든 형식의 암호화를 자동 판별한 결과가 아니다. `.age`·`.gpg` 확장자도 실제 복호화 검증 전에는 암호화 성공으로 간주하지 않는다.

추가 허용 규칙은 ACL 검토 신호다. 그룹 구성원·deny 규칙까지 계산한 유효 접근권한 판단은 아니므로 `effectiveAccessEvaluated=false`를 명시한다. 관리자·SYSTEM 권한이 필요 없는 배포 환경인지 등의 정책 판단 역시 별도다.

검토 항목이 있으면 `needs_attention`과 종료 코드 1을 반환한다. 현재 이 결과는 알려진 평문 백업·상속 권한을 표시하는 정상적인 경고이며 사이트 장애가 아니다. 자체 테스트 11개 통과, 기존 서버 점검 10항목 정상.

## 암호화 방식 — 선택 전, 실제 적용 안 함

다른 PC에서도 복구할 수 있어야 하므로 사용자 보관 암호 또는 별도 비밀키 방식을 후보로 둔다. 암호·비밀키 자체를 채팅으로 받거나 작업 기록에 남기지 않는다.

| 후보 | 사용 방식·주의점 |
| --- | --- |
| 사용자 보관 암호 | 로컬 터미널에서 직접 입력. 복구 시 같은 암호 필요. 별도 안전한 위치에 보관하고 분실 대비 절차 필요 |
| 사용자 보관 비밀키 파일 | 공개키로 암호화하고 비밀키로 복호화. 자동 백업에 유리하지만 비밀키를 백업과 같은 장소에만 두면 안 됨 |
| Windows 계정/PC 종속 보호 | 계정·프로필·컴퓨터 복구 조건에 영향을 받을 수 있어 다른 PC 복구 목적의 기본안으로 확정하지 않음 |

`age`는 암호를 대화형으로 입력하는 방식과 공개키/비밀키 방식을 제공한다. 사용할 경우 검증된 배포본을 준비하고, 실제 복호화 및 기존 `recovery:restore`까지 통과한 뒤 보호 완료로 판정한다. 아직 설치하거나 실행하지 않았다. [age 공식 사용 안내](https://github.com/FiloSottile/age/blob/main/README.md)

Windows 데이터 보호의 사용자·컴퓨터 범위는 별도 복구 제약을 검토해야 한다. 이번에는 해당 방식으로 자동 전환하지 않았다. [Microsoft 데이터 보호 범위 문서](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dataprotectionscope)

## 보관·삭제 원칙

현재 적용한 안전 기준은 **자동 삭제 없음, 만료 기간 미확정, 기존 검증 백업 유지**다. 아래는 이후 보호 작업에 적용할 절차이며 아직 삭제 기능을 구현한 것은 아니다.

1. 키 방식과 사용자의 안전한 키 보관 방법을 먼저 정한다. 키를 소스 코드·`.env`·매니페스트·백업 폴더에 함께 보관하지 않는다.
2. 기존 백업을 보존한 채 암호화 사본을 만든다. 같은 이름의 기존 사본을 덮어쓰지 않는다.
3. 암호화 사본을 별도 임시 위치에 복호화하고 파일 무결성·원본 없는 복원 검증을 다시 수행한다.
4. 복호화 키 보관·다른 장치 복구 방법을 사용자가 확인한다. 확인 전에는 평문 원본을 삭제하지 않는다.
5. 평문 원본과 임시 복호화본의 정리는 정확한 경로·포함 데이터·삭제 범위에 대한 사용자 승인 후 수행한다. 일반 파일 삭제가 디스크의 안전한 완전 삭제를 보장한다고 설명하지 않는다.
6. 보관 주기·오래된 사본 정리 기준은 사용자 승인 후 정한다. 날짜가 오래됐다는 이유만으로 마지막 검증 사본을 자동 삭제하지 않는다.

외부 백업 저장 위치·클라우드 업로드·유료 서비스·접근 계정 추가는 별도 승인 대상이다. 이번에는 어떤 백업도 전송하거나 삭제하지 않았다.

## 변경과 복구

`scripts/backup-security-check.ps1`과 package.json 명령 2개, README·정책 문서를 추가했다. 이를 제거하면 점검 도구만 없어지며 원본 데이터·ACL·백업 내용은 그대로다. 실제 암호화·접근 제한 적용은 사용자 선택 후 진행한다.
