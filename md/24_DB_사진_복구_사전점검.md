# DB·사진 복구 사전 점검

## 확인된 차이

기존 `db:backup:verify`는 PostgreSQL 덤프를 만들고 같은 PostgreSQL 컨테이너의 별도 임시 DB에 복원해 테이블·사용자·매물 개수를 조회한다. MinIO 사진 파일은 포함되지 않는다. 테이블이 1개 이상인지 확인하지만 백업 시점의 전체 내용·개수와 대조하지는 않는다. 기존 도구는 이번에 변경하거나 실행하지 않았다.

`listing_images`의 READY 사진은 처리된 WebP 본문·썸네일을 참조한다. `size_bytes`는 변환된 본문 크기로 갱신되지만 `sha256`은 업로드 당시 파일 값으로 남는다. DB 해시를 변환 사진과 직접 비교하면 정상 파일도 손상으로 오판할 수 있다. 근거는 `listing-images.service.ts` 업로드 레코드 생성과 `listing-image-processing.service.ts` READY 전환 코드다.

## 실행과 안전 범위

```powershell
npm.cmd run recovery:preflight
npm.cmd run test:recovery:preflight
```

실행 중인 로컬 PostgreSQL·MinIO와 `.env` 연결 설정이 필요하다. 동일한 프로세스 환경변수가 있으면 우선한다.

- DB·저장소는 localhost·루프백만 허용. DB URL의 추가 호스트 지정 등도 거부
- DB 세션을 읽기 전용으로 설정하고 실제 `transaction_read_only=on` 확인
- 사진 레코드 최대 10,000개. 초과하면 저장소 요청 전에 중단
- READY 본문·썸네일에 HEAD 요청만 전송. 사진 내용을 다운로드하거나 저장하지 않음
- 본문 크기는 DB와 비교, 썸네일 크기는 양수인지 확인. MIME도 대조
- 저장소 요청은 최대 4개 동시 실행, 요청당 5초 제한·재시도 없음
- 처리 중 UPLOADED·SCANNING 사진 또는 점검 전후 DB 참조 변경은 확인 필요로 판정
- 인증정보·객체 키·사진별 ID·원문 오류는 출력하지 않음

정상은 `ok`, 누락·접근 실패·메타데이터 불일치·참조 변경·처리 중 사진은 `needs_attention`이다. READY 사진이 없으면 `no_ready_images`로 구분한다. `ok` 이외 결과와 실행 오류는 종료 코드 1이다.

테스트 17개·포맷 검사 통과. 00:03:48 KST 기존 서버 점검 10항목 정상, 주소 지오코딩·외부 경보 비활성 유지.

HEAD 검사이므로 사진 바이트 손상·디코딩 가능 여부는 검증하지 않았다. REJECTED 사진은 개수만 집계했다. 버킷 고아 객체·정적 샘플 사진·다른 DB 테이블은 검사 범위 밖이다. 점검 전후 DB 참조가 같아도 중간 객체 변경이나 DB·저장소의 원자적 스냅샷을 보장하지 않는다. 출력에 `backupCreated=false`, `restorePerformed=false`를 명시한다.

## 후속 통합 백업·복원 설계

아래는 사전 점검 시 정리한 설계다. 이후 구현·실행한 범위와 제한은 [25번 실제 검증 결과](./25_DB_사진_통합백업_격리복원_검증.md)에 기록했다. 이 문서의 사전 점검 명령 자체는 계속 읽기 전용이며 백업·복원을 수행하지 않는다.

1. DB 전체, READY 본문·썸네일, 정적 샘플 자산 및 REJECTED/격리 파일의 포함·제외 정책을 명시한다. 처리 중 사진이 있으면 완성된 백업으로 판정하지 않는다.
2. DB 덤프와 사진 참조 목록이 같은 DB 스냅샷을 사용하도록 구성한다. 파일 삭제·변환과의 경합을 처리해야 한다. 현재 앱·워커를 임의 중단하지 않으며 중단이 필요한 방식은 사용자와 범위를 확인한다. 파일 누락·변경 시 불완전 백업으로 실패 처리한다.
3. 고유 실행 ID의 로컬 `backups` 하위 폴더에 덤프와 사진 복사본을 모은다. 복사한 바이트에서 새 SHA-256을 계산하고 키·파일·크기·해시를 매니페스트로 연결한다. 기존 업로드 해시를 변환 사진 해시로 해석하지 않는다.
4. 복원 대상은 원본과 다른 프로젝트·볼륨·인증정보·네트워크의 임시 PostgreSQL·MinIO만 허용한다. 원본과 대상 식별자가 다름을 확인한다. 복원용 앱·워커·메일 전송은 실행하지 않는다.
5. 덤프 복원 후 테이블별 수치와 중요 관계를 백업 시점 명세와 대조한다. 복원 저장소의 모든 READY 참조를 확인하고 복원 바이트의 SHA-256·크기·이미지 디코딩·대표 사진·순서를 대조한다.
6. 누락·해시 불일치 시험은 임시 복원본에서만 수행한다. 원본 파일을 삭제·변조하지 않는다.
7. 실행 시 생성한 자원 ID를 대조한 뒤 임시 자원만 정리한다. 백업은 개인정보를 포함할 수 있으므로 보관 위치·정책을 안내하고 외부로 업로드하지 않는다.

`backups/`의 Git·Docker 빌드 제외는 암호화나 접근 통제를 대신하지 않는다. 이번에는 백업 파일·복원 DB·버킷·사진 복사본을 만들지 않았다.

기존 DB 검사 도구를 재사용하려면 명령별 종료 코드, 파일명 충돌, 복원 수치 비교, 정리 실패 판정도 보강해야 한다. 특히 현재 `temporaryDatabaseRemoved=true`는 정리 결과 확인 전 만들어지므로 정리 성공 증거로 사용할 수 없다.

## 변경과 복구

`scripts/recovery-preflight.mjs`, 테스트 파일, package.json 명령 2개를 추가했다. 기존 pg·S3 SDK를 사용해 의존성 설치·앱 재빌드는 필요 없다. 기존 DB 백업 스크립트·앱·데이터·컨테이너는 변경하지 않았다. 복구 시 이번 파일 2개와 명령 추가만 제거하면 되며 데이터 정리는 필요 없다.
