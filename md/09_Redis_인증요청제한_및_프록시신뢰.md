# Redis 인증 요청 제한과 프록시 신뢰

## 작업 결과

회원가입·이메일 확인·로그인 API에 분산 환경용 요청 제한을 적용했다. 여러 API 인스턴스가 동시에 요청을 받아도 Redis가 공통 카운터를 관리하며, 제한을 넘은 요청은 비밀번호 해시 계산이나 데이터베이스 조회 전에 `429 Too Many Requests`로 차단한다.

## 구성 요소의 역할과 필요한 이유

| 구성 요소 | 역할 | 필요한 이유 |
|---|---|---|
| `RateLimits` 데코레이터 | 각 API에 제한 수치·시간·식별 기준을 선언 | 보안 정책을 컨트롤러에서 쉽게 확인하고 엔드포인트별로 조정하기 위해 필요 |
| `RateLimitGuard` | 본 기능 실행 전에 제한을 소비하고 초과 시 `429`와 `Retry-After` 반환 | 무차별 로그인, 대량 가입, 확인 토큰 대입으로 발생하는 자원 소모와 계정 공격을 줄이기 위해 필요 |
| `RateLimitService` | IP·이메일을 정규화하고 HMAC 지문 키로 변환 | Redis 운영자나 키 덤프에 개인정보 원문이 노출되는 일을 줄이기 위해 필요 |
| Redis Lua 연산 | 카운터 증가와 최초 만료 설정을 하나의 원자 작업으로 실행 | 여러 서버의 동시 요청에서도 증가 값 누락과 만료 없는 카운터가 생기지 않게 하기 위해 필요 |
| `TRUST_PROXY_HOPS` | Express가 신뢰할 프록시 홉 수를 명시 | 로드 밸런서 뒤에서 실제 클라이언트 IP를 사용하되, 직접 접속 환경에서 위조한 전달 헤더를 신뢰하지 않기 위해 필요 |
| Docker 빌더 OpenSSL | Prisma 생성 단계가 사용할 암호화 라이브러리 환경을 명확히 제공 | 빌드 시 OpenSSL 버전 추측 경고를 제거하고 재현성을 높이기 위해 필요 |

## 초기 제한 정책

| API | 식별 기준 | 제한 |
|---|---|---|
| 회원가입 | IP | 15분에 10회 |
| 이메일 확인 | IP | 15분에 30회 |
| 로그인 | IP | 15분에 60회 |
| 로그인 | 정규화한 이메일 | 15분에 10회 |

IP 제한은 다수 계정을 바꿔 가며 공격하는 상황을 줄이고, 이메일 제한은 여러 IP를 이용해 한 계정을 공격하는 상황을 줄인다. 고정 구간 방식은 구현과 운영이 단순한 초기 정책이며, 실제 트래픽과 오탐 지표를 수집한 뒤 슬라이딩 구간 또는 토큰 버킷으로 교체할 수 있다.

## 장애 정책

- `local`·`test`: Redis를 구성하지 않았거나 일시적으로 사용할 수 없으면 개발·독립 E2E 테스트를 위해 요청 제한만 건너뛴다.
- `staging`·`production`: Redis 요청 제한을 사용할 수 없으면 인증 엔드포인트가 `503`을 반환한다. 보호 장치가 사라진 상태에서 민감한 API를 계속 공개하지 않는 실패 폐쇄 정책이다.
- readiness는 기존과 같이 Redis 장애를 감지하므로 로드 밸런서가 비정상 API 인스턴스를 트래픽에서 제외할 수 있다.

## 프록시 배포 주의사항

로컬 직접 접속은 `TRUST_PROXY_HOPS=0`이다. 운영에서는 애플리케이션 앞의 신뢰 가능한 로드 밸런서·리버스 프록시 홉 수와 정확히 같은 값을 설정해야 한다. 실제 경로보다 크게 설정하면 공격자가 `X-Forwarded-For`를 위조할 여지가 생기고, 설정하지 않으면 모든 사용자가 프록시 한 IP로 묶일 수 있다.

## 검증 결과

- 서비스 단위 테스트: 허용·차단 계산과 이메일 원문 미포함 Redis 키 확인
- Guard 단위 테스트: 제한 초과 시 `429`, `Retry-After` 확인
- Redis 통합 테스트: 동시 증가 10건의 결과가 1~10으로 빠짐없이 기록되고 TTL이 설정되는지 확인
- 기존 인증 통합 테스트: 이메일 확인, 계정 잠금, 세션·CSRF·로그아웃 흐름 통과
- Docker 이미지: OpenSSL을 포함한 API 빌더에서 Prisma 생성과 NestJS 빌드 성공
