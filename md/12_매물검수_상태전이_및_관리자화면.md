# 매물 검수 상태 전이 및 관리자 화면

## 작업 결과

중개사가 작성한 초안을 검수 요청하고 관리자가 승인·수정 요구·반려하는 상태 흐름을 구현했다. 모든 전환은 사용자 역할, 매물 소유권, 현재 상태, 버전을 확인하며 검수 결정과 상태 이력·감사 로그를 하나의 DB 트랜잭션으로 기록한다.

## 구성 요소의 역할과 필요한 이유

| 구성 요소 | 역할 | 필요한 이유 |
|---|---|---|
| 검수 요청 API | 중개사 소유의 `DRAFT`·`NEEDS_CHANGES`를 `REVIEW_PENDING`으로 변경 | 편집 중인 매물과 검수할 준비가 된 매물을 명확히 구분하기 위해 필요 |
| 관리자 대기열 | `REVIEW_PENDING` 매물만 오래된 요청 순서로 제공 | 검수 대상 누락을 줄이고 공정한 처리 순서를 유지하기 위해 필요 |
| 관리자 역할 Guard | `ADMIN`만 대기열과 결정 API에 접근 | 중개사나 일반 사용자가 스스로 승인하는 권한 상승을 막기 위해 필요 |
| 상태 전이 규칙 | 허용된 출발 상태에서만 다음 상태로 변경 | 이미 처리된 요청의 중복 승인이나 잘못된 순서의 상태 변경을 방지하기 위해 필요 |
| 버전 기반 잠금 | 제출·결정 시 화면 버전과 DB 버전을 비교 | 관리자가 보고 있는 동안 매물이 바뀌었을 때 오래된 내용으로 결정하는 일을 막기 위해 필요 |
| 검수 의견 | 수정 요구·반려 시 5자 이상의 사유를 필수 기록 | 중개사가 무엇을 고쳐야 하는지 알 수 있고 결정 근거를 남기기 위해 필요 |
| `ListingReview` | 관리자, 결정, 의견, 시점을 영구 기록 | 반복 검수와 분쟁 조사에서 각 결정의 근거를 확인하기 위해 필요 |
| 상태 이력·감사 로그 | 행위자와 이전·다음 상태, 버전을 기록 | 운영 추적과 보안 감사에 필요 |
| 중개사 화면 | 검수 요청 버튼과 최신 검수 의견 표시 | 요청과 수정 재제출을 실제 사용자 흐름으로 제공하기 위해 필요 |
| 관리자 화면 | 상세 내용과 승인·수정 요구·반려 입력 제공 | API를 직접 호출하지 않고 검수 업무를 처리하기 위해 필요 |

## 상태 흐름

1. 중개사가 `DRAFT` 또는 `NEEDS_CHANGES` 매물을 검수 요청한다.
2. 매물은 `REVIEW_PENDING`이 되며 편집할 수 없다.
3. 관리자는 다음 중 하나를 결정한다.
   - `APPROVED`: 검수 통과. 아직 공개되지 않는다.
   - `NEEDS_CHANGES`: 의견과 함께 중개사 편집 단계로 돌아간다.
   - `REJECTED`: 반려 상태로 종료한다.
4. `NEEDS_CHANGES` 매물은 중개사가 수정 후 다시 검수 요청할 수 있다.

`APPROVED`와 `PUBLISHED`를 분리했다. 검수 통과와 실제 공개를 별도 권한·시점으로 관리하기 위한 설계이며 게시 기능은 다음 단계에서 구현한다.

## API와 화면

- `POST /api/v1/listings/:id/submit-review`: 중개사 검수 요청
- `GET /api/v1/listings/review-queue`: 관리자 검수 대기열
- `POST /api/v1/listings/:id/review`: 관리자 결정
- `/agent/listings`: 검수 요청과 검수 의견 확인
- `/admin/listings`: 검수 대기 목록과 결정 화면

로컬 관리자 계정은 `seed-admin@local.invalid`, 비밀번호는 `LocalAdminPassword123!`이다. 로컬·테스트 환경에서만 사용한다.

## 검증 결과

- 중개사 검수 요청 후 `REVIEW_PENDING`, 버전 증가 확인
- 중개사의 관리자 대기열 접근 `403` 확인
- 의견 없는 수정 요구 `400` 확인
- 관리자 수정 요구와 의견 저장 확인
- 중개사 수정·재제출 확인
- 관리자 승인 후 `APPROVED`와 버전 증가 확인
- 승인 상태가 아직 공개 API에 노출되지 않는 것 확인
- 검수 기록 2건, 상태 이력 7건, 감사 로그 7건 확인
- 테스트 데이터 자동 정리 확인
