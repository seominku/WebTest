# 이메일 확인·역할 검사·웹 인증 화면

## 작업 결과

가입 직후 이메일 소유 여부를 확인하는 일회용 토큰 흐름, API 역할 검사, 회원가입·로그인·내 계정 웹 화면을 연결했다. 브라우저가 세션 식별자를 직접 읽지 않도록 HttpOnly 쿠키를 유지하고, 화면에서 필요한 사용자 정보와 CSRF 토큰만 메모리에 보관한다.

## 구성 요소의 역할과 필요한 이유

| 구성 요소 | 역할 | 필요한 이유 |
|---|---|---|
| 이메일 확인 토큰 | 가입 시 24시간 유효한 256비트 일회용 값을 발급하고 서버에는 SHA-256 해시만 저장 | 임의 사용자가 다른 사람의 이메일로 활성 계정을 만드는 일을 막고, DB 유출 시에도 원문 토큰을 바로 사용할 수 없게 하기 위해 필요 |
| `POST /auth/verify-email` | 미사용·미만료 토큰을 원자적으로 소비하고 계정을 `ACTIVE`로 전환 | 같은 토큰의 재사용과 동시에 들어온 중복 확인 요청을 차단하기 위해 필요 |
| `Roles` 데코레이터와 `RolesGuard` | API별 허용 역할을 선언하고 인증 사용자의 역할을 검사 | 관리자·중개사·일반 사용자 기능이 늘어날 때 권한 규칙을 일관되게 적용하기 위해 필요 |
| `AuthProvider` | 현재 사용자와 CSRF 토큰을 브라우저 메모리에서 관리 | 새로고침 때 서버를 다시 확인하고, 장기 보관소인 `localStorage`에 인증 정보를 남기지 않기 위해 필요 |
| 회원가입 화면 | 입력값을 API에 전달하고 로컬 환경에서는 반환된 확인 토큰을 화면에 노출하지 않은 채 즉시 소비 | 실제 메일 서비스가 없는 로컬 개발에서도 운영과 같은 가입 상태 전이를 검증하기 위해 필요 |
| 로그인 화면 | 세션 쿠키 발급 후 사용자와 CSRF 상태를 공급자에 연결 | 보호 화면과 로그아웃이 같은 인증 상태를 사용하게 하기 위해 필요 |
| 내 계정 화면 | 로그인 사용자·역할을 표시하고 최신 CSRF 토큰으로 로그아웃 | 세션 유효 여부와 권한 정보를 사용자에게 보여 주고 안전하게 세션을 폐기하기 위해 필요 |
| 인증 스모크 테스트 | 실행 중인 Docker API에 가입부터 폐기된 세션 거부까지 실제 HTTP 요청 | 단위 테스트뿐 아니라 쿠키·CORS·DB·Redis를 포함한 배포 형태의 연결 상태를 확인하기 위해 필요 |

## 보안 흐름

1. 가입하면 사용자는 `PENDING_VERIFICATION` 상태가 되고 이메일 확인 토큰의 해시가 DB에 저장된다.
2. 토큰을 확인하면 `consumed_at`이 기록되고 사용자는 `ACTIVE`가 된다. 소비됐거나 만료된 토큰은 거부된다.
3. 로그인하면 세션 원문은 HttpOnly 쿠키로만 전달되고, 서버는 세션 해시를 PostgreSQL에 저장한다.
4. 웹은 `/auth/me`로 세션을 확인한 뒤 `/auth/csrf`로 최신 CSRF 토큰을 받는다.
5. 로그아웃은 신뢰한 Origin, JSON 요청, 세션 쿠키, 최신 CSRF 토큰을 모두 확인한 후 세션을 폐기한다.

## 환경별 이메일 확인 처리

- `local`·`test`: 가입 응답에 확인 토큰을 제공한다. 웹은 이 값을 렌더링하거나 저장하지 않고 즉시 확인 API로 보낸다.
- `staging`·`production`: 가입 응답에 토큰을 포함하지 않는다. 운영 메일 발송 어댑터가 링크 또는 코드를 전달해야 한다.

따라서 현재 로컬 인증 흐름은 완성됐지만 실제 이메일 발송은 아직 연결되지 않았다. 운영 배포 전에는 메일 제공자, 재전송 API, 재전송 빈도 제한, 만료 안내 화면을 추가해야 한다.
