# 부동산 웹사이트 서버 및 기술 스택 선정

## 1. 최종 권장안

이 프로젝트는 다음 조합으로 시작한다.

- 프론트엔드: **Next.js App Router + TypeScript**
- API 서버: **NestJS + TypeScript**
- 런타임: **Node.js 24 LTS**
- 데이터베이스: **PostgreSQL**
- ORM 및 마이그레이션: **Prisma**
- 캐시 및 세션 저장소: **Redis**
- 비동기 작업: **BullMQ + Redis**
- 매물 이미지: **S3 호환 오브젝트 저장소**
- 로컬 개발 환경: **Docker Compose**
- 스테이징 및 운영형 환경: **AWS 서울 리전, ECS Fargate**
- 트래픽 진입점: **Route 53 -> CloudFront -> AWS WAF -> ALB**
- 로그 및 경고: **CloudWatch**
- 비밀정보: **AWS Secrets Manager**

처음에는 마이크로서비스로 분리하지 않고, 프론트엔드와 API 서버만 구분한 **모듈형 모놀리스**로 개발한다.

## 2. 권장 아키텍처

```text
사용자
  |
  v
Route 53
  |
  v
CloudFront + AWS WAF + Shield
  |
  v
Application Load Balancer
  |-----------------------|
  v                       v
Next.js 웹 서버       NestJS API 서버
                          |
            |-------------|-------------|
            v             v             v
      RDS PostgreSQL    Redis           S3

CloudWatch     <- 로그, 지표, 경고
Secrets Manager <- DB 비밀번호, API 키, 비밀정보
```

## 4. 이 구성을 선택한 이유

### 4.1 보안 책임을 명확하게 분리할 수 있다

- Next.js는 화면과 서버 렌더링을 담당한다.
- NestJS는 인증, 권한, 입력 검증, 감사 로그를 담당한다.
- 데이터베이스와 Redis는 인터넷에서 직접 접근할 수 없게 구성한다.
- 이미지 파일은 애플리케이션 디스크가 아니라 별도 저장소에서 관리한다.
- WAF와 애플리케이션 요청 제한을 함께 사용한다.

### 4.2 문제 탐지와 복구 훈련에 적합하다

- 웹과 API를 독립적으로 재배포하고 롤백할 수 있다.
- 컨테이너 장애와 자동 재시작을 연습할 수 있다.
- 잘못된 배포, 외부 API 장애, DB 장애를 계층별로 분리해 조사할 수 있다.
- CloudWatch 로그와 지표를 이용해 MTTD와 MTTR을 측정할 수 있다.
- RDS 백업과 시점 복구를 실제로 연습할 수 있다.

### 4.3 유지보수가 쉽다

- 프론트엔드와 백엔드가 모두 TypeScript를 사용한다.
- 도메인별 NestJS 모듈로 기능을 분리할 수 있다.
- Docker 이미지를 개발, 스테이징, 운영에 공통으로 사용할 수 있다.
- 기능 플래그와 작은 배포 단위를 적용하기 쉽다.

## 5. 환경별 구성

### 5.1 로컬 개발

Docker Compose에서 다음 서비스를 실행한다.

```text
Next.js
NestJS
PostgreSQL
Redis
MinIO 또는 로컬 S3 호환 저장소
```

목적:

- 개발 환경 재현
- DB·Redis·이미지 저장소 장애 연습
- 자동 테스트 실행
- 외부 서비스 비용 없이 기능 개발

### 5.2 스테이징

- ECS Fargate: Next.js 1개, NestJS 1개부터 시작
- RDS PostgreSQL: 개발·검증용 소형 구성
- Redis: 세션과 요청 제한 저장
- S3: 테스트용 매물 이미지
- CloudFront, WAF, CloudWatch, Secrets Manager
- 가상 매물과 테스트 계정만 사용

모든 보안 공격과 장애 주입 훈련은 스테이징에서 먼저 수행한다.

### 5.3 운영형 훈련

- 웹과 API 컨테이너를 각각 2개 이상 실행
- 다중 가용 영역 구성
- RDS Multi-AZ 적용
- 자동 배포와 자동·수동 롤백 검증
- 관리자 MFA와 중앙 감사 로그
- 백업 복원용 별도 환경
- WAF 요청 제한과 비상 차단 규칙

## 7. 프로젝트 폴더 구조

```text
real-estate-platform/
├─ apps/
│  ├─ web/                 # Next.js
│  └─ api/                 # NestJS
├─ packages/
│  ├─ db/                  # Prisma 스키마와 마이그레이션
│  ├─ shared/              # 공통 타입과 검증 스키마
│  └─ config/              # 공통 린트와 TypeScript 설정
├─ infrastructure/         # Docker와 향후 AWS 인프라 정의
├─ tests/                  # 통합·보안·장애 훈련 테스트
├─ docs/                   # 프로젝트 내부 기술 문서
└─ docker-compose.yml
```

## 8. 처음부터 사용하지 않을 구성

- Next.js 한 서버에 모든 책임을 몰아넣는 구조
- PostgreSQL을 웹 서버와 같은 컨테이너에서 운영하는 구성
- 처음부터 마이크로서비스 또는 Kubernetes를 도입하는 구성
- 운영 서버에 직접 접속해 코드를 수정하는 방식
- 매물 이미지를 서버 로컬 디스크에만 저장하는 방식
- 자체 제작 암호화 또는 검증되지 않은 로그인 구현
- 개발·스테이징·운영이 같은 데이터베이스를 사용하는 구성
- 복원 시험이 없는 형식적인 백업

## 9. 버전과 유지보수 원칙

- Node.js는 Active LTS 또는 Maintenance LTS만 사용한다.
- 초기 기준 런타임은 Node.js 24 LTS로 고정한다.
- 패키지 잠금 파일을 커밋한다.
- 의존성 업데이트는 자동 테스트와 스테이징 검증 후 적용한다.
- 런타임과 주요 프레임워크 업그레이드 날짜를 작업 기록에 남긴다.
- 지원 종료 버전은 신규 기능보다 우선해 교체 계획을 세운다.

## 10. 비용과 복잡도 주의사항

AWS의 ALB, NAT Gateway, RDS, WAF 등의 서비스는 사용량이 적어도 고정 비용이 발생할 수 있다. 따라서 다음 순서로 진행한다.

1. 로컬 Docker Compose로 MVP 개발
2. 스테이징이 필요할 때 AWS 최소 구성 배포
3. 보안과 장애 훈련이 시작될 때 WAF·경고·백업 강화
4. 실제 공개를 결정할 때 다중 가용 영역과 운영형 구성 적용

정확한 비용은 배포 직전에 최신 AWS 요금표와 예상 트래픽을 기준으로 다시 계산한다.
