# 원본 연결 없이 기존 백업 복원 검증

## 완료한 기능

이전에는 `recovery:verify`가 원본에서 새 백업을 만든 뒤 그 백업만 검증했다. 이제 `recovery:restore`로 보관된 백업을 지정할 수 있다. 이 분기는 원본 `.env`를 읽거나 원본 PostgreSQL·MinIO에 연결하지 않는다. 기존 복원·사진 결함 검사·소유 자원 정리 코드를 공유한다.

```powershell
npm.cmd run recovery:restore -- backups/recovery-759f1a91-15ec-4b0c-8bfb-68131bdd052e
```

새 백업을 생성하는 기존 `recovery:verify` 명령은 유지한다. 인자를 빠뜨린 `recovery:restore`는 오류로 종료하며 새 백업 생성 모드로 넘어가지 않는다.

복원 검증에는 Node·npm 의존성, Docker Desktop, 고정된 로컬 PostgreSQL·MinIO·검사용 이미지가 필요하다. 원본 앱 서버가 필요 없다는 뜻이지 실행 도구나 이미지도 필요 없다는 뜻은 아니다. 다른 PC에서 필요한 이미지·검사 코드를 별도로 준비하는 절차는 아직 남아 있다.

## 파일 검증과 보존

- 프로젝트 `backups/recovery-UUID` 바로 아래의 백업만 허용하고 다른 경로·임의 디렉터리 이름·잘못된 인자를 거부
- 백업 디렉터리의 심볼릭 링크·junction, 파일의 심볼릭 링크·하드 링크를 거부
- 완료된 매니페스트인지, 디렉터리와 실행 ID가 일치하는지, 사진 참조가 빠짐없이 포함되는지 확인
- PostgreSQL custom 덤프 식별자와 SHA-256, 사진별 크기·SHA-256을 복원용 Docker 자원 생성 전에 검사
- 파일명 경로 이탈·누락·손상·중복·처리 중 사진 상태를 거부
- 검증 대상 파일 묶음의 해시를 복원 직전과 검증 완료 후 다시 비교
- 기존 백업과 그 안의 `verification.json`은 덮어쓰지 않음. 새 결과는 `.artifacts/recovery-restore-새실행ID/verification.json`에 저장

제한은 매니페스트 2MiB, 덤프 128MiB, 개별 사진 16MiB, 사진 합계 256MiB, 테이블 100개·총 100,000행·사진 레코드 1,000개다. 초과 시 별도 대용량 복구 방식을 준비해야 한다.

해시는 매니페스트와 파일의 일치 여부를 확인한다. 서명이나 신뢰할 수 있는 외부 해시가 없으므로 매니페스트까지 고친 악의적인 위조를 인증하는 기능은 아니다. 신뢰할 수 있는 자체 백업에만 사용하며 실행 중 파일을 편집하지 않는다. 백업의 암호화·ACL·보관 주기는 아직 별도 과제다.

## 실제 원본 미접근 검증

검증 실행 ID: `17162514-33fd-45c3-b2f5-aab85b884b46`

입력은 이전 작업의 `backups/recovery-759f1a91-15ec-4b0c-8bfb-68131bdd052e/`를 그대로 사용했다. 새 DB 덤프나 사진 백업을 생성하지 않았다.

테스트 전용 preload `scripts/fixtures/recovery-source-deny.mjs`로 부모 검사 프로세스의 `.env` 읽기와 직접 TCP 연결을 오류로 만들었다. Docker CLI는 로컬 Docker 엔진을 통해 격리된 임시 컨테이너를 실행한다. 이 가드는 시스템 방화벽이나 모든 자식 프로세스의 네트워크 차단 도구가 아니라 부모 검사 코드가 원본 경로를 사용하지 않는지 확인하는 테스트 장치다.

```powershell
node --import ./scripts/fixtures/recovery-source-deny.mjs ./scripts/recovery-bundle-check.mjs --from-backup backups/recovery-759f1a91-15ec-4b0c-8bfb-68131bdd052e
```

새 결과 파일은 `.artifacts/recovery-restore-17162514-33fd-45c3-b2f5-aab85b884b46/verification.json`이다. 도구 내부의 매니페스트·덤프·사진 검증 외에도 기존 결과 파일까지 포함한 14개 파일 전체를 별도 비교해 원본 백업 보존을 확인했다.

가드가 실제 작동하는지도 대조했다. 같은 가드를 켠 채 원본 캡처 모드를 실행하면 `SOURCE_ENV_ACCESS_FORBIDDEN`으로 즉시 실패했고 자원을 생성하지 않았다. TCP 가드는 별도 자동 테스트에서 연결 전에 오류를 발생시키는 것을 확인했다.

테스트 총 50개 통과. 검사 테스트에서 발견한 Windows `--import` 절대 경로 전달 문제는 파일 URL 사용으로 수정했다. 실제 원본 미접근 실행은 상대 경로 preload로 정상 수행됐다. 02:23:37 기존 앱 상태 점검 10항목 정상, 주소 지오코딩·외부 경보 비활성 유지.

## 보안·한계와 다음 작업

기존 앱·DB·저장소를 멈추지 않았다. 임시 복원 자원만 삭제했으며 기존 백업의 민감 자료는 그대로 남아 있다. 외부 업로드·이메일·메신저 발송은 하지 않았다.

이 기능은 백업의 복원 가능성 검사이며 복원된 서비스로 사용자를 전환하거나 웹 앱을 실행하는 기능은 아니다. DB 역할·원래 권한·Redis 상태·REJECTED/고아 파일 등의 제외 범위는 25번 문서와 동일하다.

다음 우선순위는 백업 접근 통제·암호화·보관 정책이다. 사용자 선택 없이 백업을 자동 삭제하거나 복호화 키의 보관 위치·방식을 임의 확정하지 않는다.

## 변경과 복구

기존 `recovery-bundle-check.mjs`에 입력 모드 분기를 추가하고, `recovery-bundle-input.mjs`, 입력 검사 테스트, 원본 접근 차단 테스트 장치를 추가했다. package.json에 `recovery:restore`를 연결하고 기존 테스트 명령을 확장했다.

이번 분기·입력 검사·테스트·명령 추가만 되돌리면 이전 새 백업 생성·검증 모드로 돌아갈 수 있다. 기존 백업과 새 결과 파일은 코드 복구 과정에서 삭제하지 않는다. 실패나 정리 문제가 있으면 종료 코드 1이며 정리 실패 내용을 별도 표시한다.
